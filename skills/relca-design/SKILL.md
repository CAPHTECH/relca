# relca-design

Relca は良い設計を自動では出さない。できるのは三つである。

- 悪い案を反例か確率の超過で落とす。
- 検査そのものが効いているかを確かめる。
- 残った案の取引と、外したものを説明できる形にする。

このスキルは、その三つを順に回して設計を良くしていく手順である。
モデルの書き方・回し方・報告は [relca-model](../relca-model/SKILL.md) に従う。ここではその上に乗る設計の改訂だけを扱う。

参照:

- `references/invoice-walkthrough.md` 請求書の例で全手順を回した記録。手計算と relca の出力の照合つき
- `examples/as-is-strengthened.relca` 手順2で契約を足した現行案
- `examples/to-be-a-review.relca` 手順4で直した AI 抽出の案
- `scripts/test_design_examples.py` 上の記録の主張を relca で再実行する検査

## 良い設計の条件

次の7つを、このスキルが目指す「良い設計」とする。Relca が定義したものではなく、作業の目標である。

| 条件 | 確かめる手順 |
|---|---|
| 破ってはいけない線(統制・安全・品質の上限)を守る | 1・3・4 |
| その線を見る検査が、壊したら捕まえる | 2・4 |
| 何を何と引き換えたか(時間・費用・品質・人の負荷)を言える | 5 |
| 前提が少し動いても結論が反転しない。または反転する点が分かっている | 4 |
| 判断の主体と根拠がたどれる。統制が構造の変更で消えていない | 3・4・5 |
| モデルから外したもの(Cut)と、それで失うものを言える | 0 |
| 運用でずれを見つけられる | 6 |

## 一線

- **線と目的を分ける。**線は `verify` と `contract`、目的は `metrics` と compare の `objectives` に書く。目的の良さで線の違反を相殺しない。
- **手計算を先に書く。**鍵になる量(誤り・時間・作業)は、relca を回す前に式で書く。出力を期待値に写さない。式と出力が合わなければ、モデルか式のどちらかが業務を写していない。
- **契約は業務で必要なものだけ足す。**`mutate` の見逃しを0にするために、すべての `reads` を契約へ転記しない(`docs/guide/dsl.md`「根拠源を求める契約」)。
- **`vacuous` を合格と読まない。**構造を変えた案で統制が `vacuous` になったら、統制の前件の操作がまだ呼ばれているかを確かめる。呼ばれていなければ、その統制は新しい構造では働いていない(請求書の例の ToBeA)。前件が起きない原因は他にもある(構成の適用範囲など。`docs/guide/results.md`)。
- **新しく置いた確率は仮定として残す。**直した案が新しい確率(人の確認の発見率など)に頼るなら、それを実測で確かめる条件として報告する。
- **案は選ばない。**残った案の順位付けは人の価値判断である。relca も順位を出さない。

## 手順

### 0. 問いと範囲を決める

1. 問いを1文にする。例: 「請求書の入力を AI 抽出へ移してよいか」。
2. 線と目的を分けて列挙する。
3. Cut に、外すものと失うものを書く(relca-model の一線)。
4. 鍵の量の式を書く。比較するすべての案で使う。

### 1. 現行を測る

`check` で現行案を回す。`satisfied` でなければ、案を比べる前に原因を確かめる。現行が線を越えているなら、それ自体が最初の発見である。

### 2. 現行の検査を強くする

案を比べる前に、物差しが効いているかを見る。`mutate` の見逃しを次の表で分ける。

| 見逃しの形 | 意味 | 対応 |
|---|---|---|
| 呼ばれない操作の `no_worsening`。`check` の `metrics.capabilities` に無いか、`starts.max` が 0 | 壊しても到達しない | 穴ではない。対応しない。異議・縮退の経路で呼ばれる操作は `starts` に数えられるので、ここに入れない |
| 異議経路(`contest ... route`)の操作の `no_worsening` | 根拠と版の契約は異議経路では未対応(`evidence_basis_contest_route`、`same_version_contest_route`) | 未検査として報告に残す。黙って落とさない |
| 呼ばれる操作の `no_worsening` | 検査が要求していない性質が壊れた | 業務で必要なら契約にする(根拠源は `evidence_basis`、版は `same_version`) |
| `no_assigned_check` | その変異を担当する検査が割り当てられていない | 弱さの印ではない(`docs/guide/results.md`「summary_reused と no_assigned_check」)。版の要求が業務の要件なら `same_version` を書く |
| `unsupported` / `not_applicable` の種 | その種を試せていない | 未検査として報告に残す |

契約を足したら `check` で線が変わらないことを確かめ、`mutate` をもう一度回して見逃しが動いたかを見る。
足す前に「この見逃しが検出に変わる」と予測を書いておく。外れたら理由を調べる。

### 3. 案を並べて落とす

各案を `check` する。複数の案を1つのモデルにまとめたなら、`configuration` ごとに回す。結果は次のように読む。

| 結果 | 読み方 | 次の手 |
|---|---|---|
| `invalid` `E-POL-LATENT` | 業務の判断が、観測できない真の値を読んでいる | その案は書けない。振り分けたいなら、観測できる信号を Actor の出力として足す |
| `violated`(契約・安全) | `explain` の反例が1つの例を示す | 反例の段を見て構造を直す |
| `violated`(確率) | 反例は出ない(1本の原因にしない) | 手順0の式で、どの項が効いているかを読む |
| 統制の `vacuous` | 統制の前件が一度も起きない | 前件の操作が `metrics.capabilities` で呼ばれているかを見る。構造の変更で呼ばれなくなったなら、手順4で新しい構造に合わせて統制を書き直す |
| `unsupported` | その組合せは未対応 | 未検査として残す。黙って外さない |

拒否に当たったら、案を変更する前に stderr の補足行(または JSON の `diagnostics[].detail`)を読む。
`kind` を見て、[拒否に当たったとき](../relca-model/references/unsupported.md#拒否に当たったとき)の手順を選ぶ。分析が未対応でも、意味を保って書き下せるなら、その版で検査してよい。元の書き方で何が未対応だったかは報告に残す。

違反している案に `mutate` を掛けると、違反中の性質はそれ以上悪化できない。その性質だけに効く変異は `no_worsening` になり、検出は他の性質についてだけ得られる。
請求書の例では、`to-be-a.relca` で検出11件・`no_worsening` 5件、`to-be-a-phase1.relca` ではほとんどが `no_worsening` だった。
違反している案の見逃しを穴と読まず、直した後にもう一度回す。

### 4. 違反した案の余裕を測り、直す

1. **余裕を測る。**式から、線を越える境界の値を出す。境界の両側の点のモデルを作って `check` する。
   `sensitivity` が使えればそれで回す。異議経路(`contest`)などを含むと `sensitivity_feature_combination` で拒否されるので、そのときは点ごとの `check` で代える。
2. **構造で直す。**パラメータを都合よく動かして通さない。足すのは段、根拠の読取り、差止めの位置などの構造である。
3. **統制を書き直す。**直した構造のどこに人の判断があるかを見て、職務分離・権限・根拠の契約をそこに置く。
   - 根拠の契約には2つの形がある。引数の系譜を含めて数える `evidence_basis A.c [S]` と、その操作自身の `reads` だけを数える `evidence_basis direct A.c [S]` である。
   - 確認の段に「原本を自分で読む」ことを求めるなら `direct` を使う。系譜で数える形では、上流の出力に根拠が付いているため、その段が読まなくなっても満たされたままになる。
4. **直した案を `mutate` する。**新しい段の見逃しが手順2の表で穴に当たれば、契約を足して閉じる。
5. **新しい仮定を測る。**直した案が新しく置いた確率についても、手順4.1と同じく境界を出して両側を確かめる。`W-LIN-2` は条件付き独立の仮定を指摘する。人と AI が同じ案件で誤るなら、その仮定は外れる。

### 5. 残った案を並べ、判断へ渡す

- 線を守った案だけを並べる。`compare` が使えるなら使う。使えなければ、`check` の出力を人が並べ、表の上に「compare ではない」と書く。
- `diff` で構成と判断の主体の差を見る。各変更の理由は `intent` に書く。
- 人に渡すものは次の4つ。
  - 案ごとの線の判定
  - 目的の値
  - 実測で確かめる仮定と、その境界値(例: 発見率 ≥ 0.46)
  - 確かめていない範囲

### 6. 運用で確かめ、戻る

導入後は、業務ログを `conform` で契約と照合する。境界値を持つ仮定は、試行運用で測る。境界を下回ったら手順4へ戻る。

## 引っかかりやすい点

いずれも請求書の例で1回観測したもの。

- `verify` は予約語で、Capability の名前にすると `E-SYN-0`(exit 3)になる。
- `same_version` の引数に、観測変数と同じ名前の束縛を渡すと `U-SEM-0 same_version_feature_combination` で拒否される。束縛名を変える。
- `examples/invoice/phase1.relca` では、`metrics` と `quality` の値(作業量、費用、待ち、誤登録の件数など)がすべて `not_configured` になる。最上位の `terminals` の経過時間は出る。
  - 原因は `defer Resubmission` と `defer Vendor.contest_rate` である。どちらも Actor にも `Actor.capability` にも当たらないので、relca は影響範囲が分からないとして値を全部取り下げる。
  - stderr の `W-CUT-2` に原因の `defer` が1行ずつ出る。JSON では `cut.defer_effects` に、取り下げの範囲(`withdraws`)と理由(`because`)が出る。
  - 値が要るなら、その段をモデルに書くか、`defer` を実在する Actor か `Actor.capability` に直す。関係のない操作の名前で代用しない。外した前提が隠れる。
  - 時間を比べるときは `configurations.relca` の `compare` を使った。
- やり直しは `repeat` で書ける。本体に並行(`fork` と `join all`)を置けるし、`same_version`・`evidence_basis`・`registers`、`compare`・`diff`・`sensitivity`、`metric mean.…` も使える。
  - まだ閉じている組合せがある(名前つきの `loop_feature_combination` で拒否される)。当たったものを報告に書く。
    - `repeat` の結果が、記録への登録と読取りを経由して `evidence_basis` の対象の操作へ届く形(引数や観測変数で渡す形は使える。出口ごとに調べ、書き下した版と同じ判定になる)。
    - `contest` との併用、`conform`、`join any`、入れ子。
    - `mutate` は種類で分かれる。使えるのは `evidence_missing`・`hold_delayed`・`summary_reused`・`refusal_path_cut`。本体に `fork` がある構成は `mutate` 全体が拒否される。
  - 閉じている組合せに当たり、上限の回数が小さければ、回ごとに `if` で書き下して比べる。書き下した版には、上の制限は掛からない。
  - 代償は、回数に比例してモデルが長くなること、回ごとに束縛の名前を変えること、回をまたいで値を更新できないこと。
  - 記録は [references/rework-unrolling.md](references/rework-unrolling.md)。
- 繁忙日の負荷は `simulate` で評価できる。`examples/invoice/busyday.relca` が例である。
  - 別の案件の出来事が同じ分に重なっても、順序が結果に効かないと確かめられれば進む。効く場合は `unsupported` で止まる。その場合は、方策に `dispatch after_finishes`(その分に終わった仕事を先に記録してから割り当てる)を足すと決まることがある。業務の実際の運用がそうなっているかを確かめてから足す。
  - 発生率を入れていない異議は、既定では拒否される。評価から外すなら、scenario に `contest_not_filed <当事者> on end.<終端> reason "…"` と理由つきで宣言する。外した異議への応答の契約は `inconclusive` のままになり、合格にはならない。
  - 負荷の値(稼働率、待ち)は本番用の scenario を release build で回して読む。検査用の小さい scenario の値を、負荷の結論に使わない。
  - `simulate` の値は標本の値である。全ての順序での安全性を示すものではない。

## 報告

relca-model の「報告」に加え、次を書く。

1. 手順ごとに、予測(手計算・検出に変わるはずの見逃し)と結果の対。
2. 足した契約と、それが業務で必要な理由。
3. 構造の変更と、書き直した統制。
4. 新しく置いた仮定と、その境界値。
5. 残った案の表。順位は付けない。
6. 確かめていないこと。上限、回していないコマンド、`unsupported` の種、仮定の確率。

## 検査

```sh
CARGO_NET_OFFLINE=true CARGO_PROFILE_DEV_DEBUG=0 CARGO_INCREMENTAL=0 cargo build -p relca-cli
python3 -B skills/relca-design/scripts/test_design_examples.py
```

- relca の binary が無ければ skip になる。unittest は skip でも exit 0 を返すが、skip は合格ではない。出力の `skipped` を見る。
- `RELCA_BIN=target/release/relca` で release build を使える。
- 試験が覆う主張は次のとおりで、改訂前の版か壊した版で外れることと対にしてある。
  - 見逃しの分類と、契約を足した後の変化
  - 束縛名による拒否
  - ToBeA の違反と空虚な分離
  - e_d = 0.07 の vacuous
  - 修理案の判定と `direct` の効き
  - 発見率の境界
  - 予約語
- 修理案の時間・作業・差戻しの値は、手計算との一致を見るだけで、壊した対は無い。compare の表、ToBeP と ToBeC の行は試験していない。
